# CampusHub — база даних PostgreSQL (ПР7)

Схема для користувачів, категорій, подій, реєстрацій і матеріалів CampusHub.

**Версія PostgreSQL:** 14 або новіша (використано `GENERATED ALWAYS AS IDENTITY`, `ILIKE`, `TIMESTAMPTZ`; тестувати можна на 14–17).
Якщо ви запускали на іншій версії — впишіть її сюди: `PostgreSQL ___`.

## Файли

| Файл | Призначення |
|---|---|
| `er-diagram.pdf`, `er-diagram.png` | ER-діаграма (PK, FK, кратність, обов'язкові/необов'язкові поля) |
| `schema.sql` | Таблиці, обмеження, `ON DELETE`, індекси |
| `seed.sql` | Тестові дані: 4 користувачі, 3 категорії, 6 подій, 9 реєстрацій, 4 матеріали |
| `queries.sql` | П'ять запитів із коментарями |
| `negative_tests.sql` | Негативні сценарії (кожен у транзакції з `ROLLBACK`) |

## Порядок запуску

Файли треба запускати саме в такому порядку: `schema.sql` → `seed.sql` → `queries.sql` → `negative_tests.sql`.

```powershell
# Windows PowerShell: щоб кирилиця виводилась правильно
chcp 65001
$env:PGCLIENTENCODING = "UTF8"

# 1. Створити базу (один раз)
psql -U postgres -c "CREATE DATABASE campushub ENCODING 'UTF8'"

# 2. Схема і тестові дані
psql -U postgres -d campushub -v ON_ERROR_STOP=1 -f schema.sql
psql -U postgres -d campushub -v ON_ERROR_STOP=1 -f seed.sql

# 3. Запити і негативні перевірки, результати — у текстові файли
mkdir results
psql -U postgres -d campushub -e -f queries.sql          2>&1 | Out-File -Encoding utf8 results\queries_results.txt
psql -U postgres -d campushub -e -f negative_tests.sql   2>&1 | Out-File -Encoding utf8 results\negative_results.txt
```

На Linux/macOS те саме без `chcp` і `$env:`, а перенаправлення — `> results/queries_results.txt 2>&1`.

Скрипти можна запускати повторно: `schema.sql` спочатку видаляє старі таблиці.
Можна також відкрити файли в pgAdmin (Query Tool) і зробити скриншоти результатів.

## Ідентифікатори і час

Усюди числові `BIGINT GENERATED ALWAYS AS IDENTITY`, усі моменти часу — `TIMESTAMPTZ`.
Дати подій у `seed.sql` задано відносно `CURRENT_TIMESTAMP`, тому події завжди лишаються майбутніми/минулими, коли б ви не запускали.

## Політика видалення

| Що видаляємо | Що відбувається |
|---|---|
| Користувача | його реєстрації видаляються (`CASCADE`) |
| Подію | її реєстрації та матеріали видаляються (`CASCADE`) |
| Категорію з подіями | заблоковано (`RESTRICT`) |
| Реєстрацію | користувач і подія залишаються |
| Матеріал | подія залишається |

## Що очікувати від запитів (для самоперевірки)

1. **Майбутні події** — 4 рядки: Основи PostgreSQL, Node.js для початківців, REST API: майстер-клас, Кар'єра в IT.
2. **Реєстрації user_id = 1** (Олена Коваль) — 3 рядки: Вступ до SQL, Основи PostgreSQL, Node.js для початківців.
3. **Кількість учасників** — Основи PostgreSQL 3; Вступ до SQL 2; Node.js 2; Git 1; REST API 1; Кар'єра в IT **0**.
4. **Пошук `%sql%`** — 2 рядки: Вступ до SQL, Основи PostgreSQL.
5. **Події з категоріями** — 6 рядків.

Негативні сценарії 1–6 і 9 мають закінчитись `ERROR`; у сценарії 7 лічильники змінюються
`6/9/4 → 5/7/2` з нулями осиротілих рядків, а в кінці seed лишається `4, 3, 6, 9, 4`.

## Відповіді на контрольні запитання

1. **Чому реєстрації в окремій таблиці?** Зв'язок «користувач — подія» багато-до-багатьох: один користувач на багатьох подіях, одна подія з багатьма користувачами. У реляційній БД це зберігається через проміжну таблицю, де кожен рядок — одна пара; плюс там живуть власні дані зв'язку (`registered_at`).
2. **Первинний і зовнішній ключ.** Первинний (PK) однозначно ідентифікує рядок своєї таблиці (унікальний, не NULL). Зовнішній (FK) — поле, що посилається на PK іншої таблиці й гарантує, що пов'язаний запис існує.
3. **Навіщо `UNIQUE (user_id, event_id)`?** Власний `id` унікальний для кожного рядка, тому не завадить вставити ту саму пару двічі. UNIQUE забороняє дублікат реєстрації на рівні БД.
4. **`CASCADE` і `RESTRICT`.** `CASCADE` разом із батьківським записом видаляє залежні. `RESTRICT` забороняє видалення батьківського, поки є залежні записи.
5. **Навіщо `LEFT JOIN` для підрахунку?** Звичайний `JOIN` відкине події без реєстрацій. `LEFT JOIN` залишає їх, а `COUNT(registrations.id)` не рахує NULL, тож дає 0.
6. **Чи перевіряє `CHECK (capacity > 0)` кількість учасників?** Ні, лише що місткість — додатне число. Контроль вільних місць потребує логіки застосунку в транзакції (наприклад, блокування рядка події й порівняння `COUNT` з `capacity`).
7. **Як відтворити базу?** Створити базу, потім по черзі виконати `schema.sql` і `seed.sql` (див. «Порядок запуску»).
